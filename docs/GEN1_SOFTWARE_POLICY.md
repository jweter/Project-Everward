# Generation-1 Software Policy

This document defines the first implemented automation layer for Everward's Phase 2 One Probe milestone.

## Purpose

Generation 1 is conscious and programmable, but its onboard computer is crude. The first automation system therefore proves the core fantasy without pretending the starting machine already has a sophisticated planner, agent framework, or high-level AI operating system.

The implementation rule is:

> Software may decide what command to issue, but authoritative hardware commands still resolve the physical result.

Automation never writes directly into probe mechanical state.

## Current Generation-1 limits

The first policy runtime intentionally allows:

- one active software policy;
- at most two simple condition/action rules;
- scalar conditions based on stored-energy fraction or probe temperature;
- power-allocation actions only;
- deterministic authored-order evaluation after each simulation advance;
- execution only while the computation subsystem is operational and has at least 25 W allocated.

These are capability limits of the primitive onboard computer, not permanent global limits for Everward.

Later computation generations may support more rules, richer state, compound conditions, routines, planning depth, concurrency, reusable functions, model-based prediction, goals, and autonomous agents.

## Shared command architecture

The engine-independent `ProbeRuntime` owns the policy evaluator and wraps the existing `SimulationCore`.

A matching rule calls `SimulationCore::allocate_power()` exactly as a manual power command ultimately does. It does not assign `ProbeStateSnapshot::power_allocated_*` fields itself.

```text
manual control --------------------------+
                                         |
                                         v
                                authoritative command
                                         ^
                                         |
software policy -> condition -> action --+
```

This preserves one mechanical truth for manual control and automation.

## Physical computation requirement

The Generation-1 policy executor requires at least 25 W of computation allocation and an operational computation subsystem.

If computation fails, its power allocation is shed by the existing subsystem-failure mechanic and policy execution stops.

Restoring the hardware alone does not magically restart automation. The player must restore enough computation power.

A policy is also allowed to reduce its own computation allocation below the execution threshold. If it does, the policy stops executing immediately and must be manually repowered. This behavior is intentional: early automation is powerful but clumsy and can create self-inflicted operational problems.

## First player-facing policy

The Phase-2 engineering HUD exposes a temporary preset named `gen1_basic_survival` from the Computation system.

It contains two rules:

1. if stored energy is below 60% of capacity, set sensor power to 0 W;
2. if temperature rises above 350 K, set propulsion power to 0 W.

The 60% threshold is deliberately aggressive for the Phase-2 bootstrap so the behavior can be observed immediately from EV-0001's starting state during integration testing. It is not a final balance value.

Controls while Computation is selected:

- `Enter`: install the Basic Survival policy;
- `Backspace`: clear the active policy;
- `Page Up` / `Page Down`: adjust computation power, including crossing the 25 W automation threshold.

The HUD reports whether a policy is installed and whether its executor is currently running or lacks sufficient computation power.

## Explainability

Policy installation/clearing and policy execution produce domain events. Successful policy actions also produce the same `PowerAllocationChanged` event generated by manual allocation.

Rejected policy actions are recorded rather than crashing or bypassing validation. This is the beginning of the future decision-debug view: the player must eventually be able to understand which rule attempted an action, why it ran, and why a command was accepted or rejected.

## Not implemented yet

This slice does not add:

- arbitrary text scripting;
- user-authored rule editing UI;
- compound boolean expressions;
- target-aware policies;
- movement or scan actions from policies;
- loops, functions, variables, priorities, or schedules;
- behavior generation;
- advanced planning or agent autonomy;
- persistence of policies in campaign saves.

Those capabilities should evolve with computation hardware and later Phase-2/Phase-10 systems rather than being granted wholesale to Generation 1.

## Next integration target

The next high-value work for the first-run playtest is a reproducible One Probe test environment with camera/look controls, visible movement references, and a test scan target. The software-policy layer should remain unchanged by that presentation work unless real playtest evidence reveals an integration defect.
