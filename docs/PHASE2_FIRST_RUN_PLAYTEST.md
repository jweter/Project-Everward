# Phase 2 First-Run Playtest Protocol

This protocol defines the first local Unreal Engine 5.8 integration run for **Phase 2 — One Probe**. It is narrower than the final Phase 2 product gate: it proves whether the current EV-0001 slice works end-to-end and records how it feels.

## Goal

Demonstrate in one repeatable run:

```text
observe -> inspect -> manage power -> move -> scan -> alter policy -> observe response
```

Keep **objective integration evidence** separate from **subjective playtest evidence**. A build can be mechanically correct and still feel poor.

## Preconditions

- test current `main` after PR #100 and later green fixes;
- use Unreal Engine 5.8;
- GitHub CI must be green for the tested commit;
- do not patch editor/Blueprint state just to make the run pass;
- record meaningful UBT/editor warnings and errors.

The Phase-2 environment is runtime-generated by `AEverwardGameMode`; no hand-authored `.umap` is required.

## Evidence record

Copy `playtests/phase2/first_run_observation.template.json` to a dated file, for example:

```text
playtests/phase2/2026-08-24-first-run.json
```

Validate it with:

```text
python tools/validate_phase2_first_run_observation.py playtests/phase2/2026-08-24-first-run.json
```

Screenshots/video may supplement the JSON, but the JSON is the canonical structured record.

## Test sequence

### 1. Build and launch

Open `unreal/Everward.uproject`, rebuild the C++ module if requested, enter Play In Editor, and confirm EV-0001 spawns. Record engine version, commit, build result, launch result, errors, and warnings.

**Blocking:** C++ module cannot build/load, PIE cannot start, or EV-0001 does not spawn.

### 2. Reproducible environment

Confirm the visible `PHASE-2 TARGET // SCAN-001` is present about 50 m ahead, spatial reference markers are visible, and lighting is sufficient to read the test scene.

### 3. Camera and embodiment

Test mouse orbit X/Y and mouse-wheel zoom. Confirm the probe can be inspected from useful angles without the camera becoming unusable.

### 4. HUD discovery

Observe the compact telemetry, press `Tab`, browse with `[` and `]`, and confirm Propulsion, Sensors, Computation, and Thermal Control are discoverable. Check that current power plus manual/automation availability are understandable without permanently cluttering the view.

### 5. Authoritative movement

With Propulsion selected, test:

- `W/S`: +X/-X;
- `D/A`: +Y/-Y;
- `E/Q`: +Z/-Z;
- `Space`: stop.

For each axis, verify velocity telemetry changes and spatial markers show real displacement/parallax. Verify accepted stop returns velocity to zero. The 1 m/s trims are intentionally primitive; judge whether they are cumbersome yet controllable, not whether they are final flight mechanics.

### 6. Power management

Change at least Sensors and Computation with `Page Up/Page Down`. Verify subsystem and total power update, capacity is respected, and any rejection is explained rather than silent. Observe energy/temperature response where practical.

### 7. Scan loop

With Sensors selected:

1. press `Enter` and confirm scan target `phase2-test-target-001`;
2. observe progress and allow one scan to complete;
3. start another scan and press `Backspace`;
4. confirm the cancelled scan never later completes.

Science results are not required yet; this tests the embodied command/lifecycle loop.

### 8. Primitive software policy

With Computation selected:

1. set computation below 25 W;
2. `Enter` installs `gen1_basic_survival`;
3. confirm policy is installed but executor is unavailable;
4. raise compute to at least 25 W and confirm executor runs;
5. verify a triggered rule changes the same authoritative power state seen by manual control;
6. `Backspace` clears the policy.

The temporary Basic Survival thresholds are test scaffolding, not balance targets.

### 9. Manual/automation shared state

After automation changes a subsystem allocation, manually change that subsystem again. Confirm both operate on one understandable state. Record command fighting, oscillation, or poor explanation even if the mechanics are technically correct.

### 10. Subjective assessment

Rate 1–5:

- embodiment;
- HUD clarity;
- control discoverability;
- Generation-1 clunkiness;
- movement readability;
- automation comprehension;
- desire to continue.

Low scores are useful evidence, not failures to hide.

## Required objective checks

A first-run result can be `pass` only when all of these pass:

- `unreal_cpp_build`
- `pie_launch`
- `probe_spawn`
- `test_environment_visible`
- `camera_orbit_zoom`
- `hud_system_discovery`
- `movement_x`
- `movement_y`
- `movement_z`
- `stop_command`
- `power_allocation`
- `scan_complete`
- `scan_cancel`
- `policy_install_clear`
- `policy_compute_gate`
- `manual_automation_shared_state`

Any required `fail` makes overall result `fail`; any `not_tested` makes it `partial`.

## Not blockers for this integration run

Prime Probe production art, final materials, final thruster/attitude physics, collision gameplay, real target selection, science payloads, resource extraction, Phase 3 star-system content, production save/load, polished mappings, and final HUD styling are not required for this first integration pass.

## After the run

Prioritize findings: build/crash blockers -> authoritative-state defects -> unusable controls -> misleading HUD/automation -> embodiment/feel -> cosmetics.

Passing this protocol means the One Probe slice is **integrated and testable**. It does not automatically satisfy the roadmap gate, **"simply existing as the probe is compelling."** That gate requires iteration on the evidence captured here.
