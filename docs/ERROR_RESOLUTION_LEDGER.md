## 2026-08-23 — Deliberate mutation audit of `simulation_core_tests.cpp`'s pre-NDEBUG-fix assertions

- **Why this audit:** the 2026-08-22 NDEBUG entry below established that every `assert()` in `simulation_core_tests.cpp` was silently disabled by CI's Release build for every simulation-core PR from #68 through the fix. That entry's own re-verification pass confirmed the whole suite still passed once assertions were made real and fixed one stale test it happened to find, but it was explicit that this was only an incidental full-suite pass, not a deliberate per-assertion mutation audit — leaving open whether any other pre-fix assertion was vacuous (structurally unable to fail) rather than merely currently-passing. `docs/PROJECT_STATUS.md`'s continuation note named this systematic audit as a dedicated near-term slice three times without it being done. This entry closes that gap for the tests written before the fix landed (movement/tick, `ScanCommand` validation and happy path, `PowerAllocationCommand` validation and happy path — lines 27-200 as of this audit) via targeted mutation testing. Tests added after the fix (`EnergyConsumption` onward) were each already mutation-verified at the PR that introduced them, per their own descriptions, so were not re-audited here.
- **Method:** nine targeted mutations, each isolated to one production code path under test, applied one at a time to `src/simulation/include/everward/simulation/core.hpp`, rebuilt and re-run via the exact CI command (`cmake -S src/simulation -B build/simulation -DCMAKE_BUILD_TYPE=Release && cmake --build build/simulation --parallel 2 && ctest --test-dir build/simulation --output-on-failure`), then reverted and diffed byte-identical against the pre-mutation file before the next mutation.
- **Result:** 8 of 9 mutations were caught cleanly, each failing the exact assertion expected: `advance_wall_ticks`'s position-integration math (transposed `velocity_mps.x`/`.y`), `start_scan`'s empty-target guard, its duration guard, `integrate_scan`'s completion threshold, `allocate_power`'s negative-watts guard, its over-capacity guard, its per-subsystem allocation switch (Sensors writing into Propulsion), and `advance_wall_ticks`'s `SimulationAdvanced` event emission (this last mutation alone broke the `events.size() == 3` assertion and would have cascaded into most other tests' own event-count assertions, confirming how much of the suite's event-accounting depends on it).
- **Finding, not a defect:** the 9th mutation — loosening `SimulationCore::advance_wall_ticks`'s own `wall_ticks < 0` guard — was **not** caught: `advance_wall_ticks(-1)` still throws `std::invalid_argument` and the test (`assert(threw)`) still passes, because `SimulationClock::advance_by()` (called immediately after, inside `advance_wall_ticks`) has its own independent `delta_ticks < 0` guard that fires first. The test's assertion is still true and the behavior is still correct — this is legitimate defense-in-depth, not a bug — but the test does not actually exercise `SimulationCore`'s own guard in isolation: removing that guard entirely would currently go undetected by this test, silently relying on `SimulationClock`'s guard alone. Recorded here rather than "fixed" because there is nothing incorrect to fix; a future slice touching this validation should know the coverage is redundant, not duplicated-and-independent.
- **Verification:** all nine mutations and their reverts are captured above; the final revert was diffed against the pre-audit file (`diff` reported no differences) and the full suite re-built and re-run clean (`100% tests passed, 0 tests failed out of 1`) before this entry was written.
- **Prevention / scope:** this closes the specific gap PROJECT_STATUS.md named for the pre-fix era of this file. It does not claim every assertion in every later slice (`EnergyGeneration` onward, `SubsystemOperationalState` onward) is mutation-verified by this entry — those were each already verified at their own introducing PR per that PR's own description, which this audit did not attempt to independently re-verify.

## 2026-08-22 — Active scans completed while sensor hardware was failed

- **Observed symptom:** post-merge review of PR #83 found that `set_subsystem_operational(Sensors, false)` correctly blocked new scans but an already-active scan continued losing `scan_remaining_s` and eventually emitted `ScanCompleted` while the sensors remained failed.
- **Root cause:** `start_scan()` validated `can_scan`, but `integrate_scan()` checked only `is_scanning`; the new operational-state transition refreshed capability flags without making scan progression honor them.
- **Fix:** `integrate_scan()` now makes no progress whenever `can_scan` is false. It preserves the active target and remaining duration, emits no completion event during the lockout, and resumes the same scan after sensor, energy, and thermal lockouts all clear.
- **Regression protection:** Release-mode CTest starts a scan, records partial progress, fails sensors, advances well beyond the remaining duration, verifies state/progress remain preserved and no `ScanCompleted` event exists, restores sensors, and verifies exactly one completion after the preserved duration elapses.
- **Residual risk:** failure currently pauses rather than cancels because no cancellation command/event contract exists. A future explicit abort mechanic must define its own state transition and event rather than silently discarding the active scan.

## 2026-08-17 — Rendering benchmark test import failed on Python 3.12

- **Observed failure:** `Foundation checks` failed while importing `prototypes/rendering-benchmark/test_benchmark.py`; all earlier Phase 1 prototype suites passed.
- **Error:** `AttributeError: 'NoneType' object has no attribute '__dict__'` inside `dataclasses._is_type` while applying `@dataclass` in `benchmark.py`.
- **Root cause:** the test loaded `benchmark.py` with `importlib.util.module_from_spec()` and executed it directly without first registering the module in `sys.modules`. Python 3.12 `dataclasses` resolves annotation/module context through `sys.modules[cls.__module__]`, so the nonstandard loader left that lookup missing.
- **Fix:** register the dynamically created module in `sys.modules` before `spec.loader.exec_module(benchmark)`.
- **Scope:** test-loader correction only; no benchmark scoring or production simulation behavior changed.
- **Prevention:** when tests dynamically load modules that define dataclasses or other module-introspective constructs, emulate normal import semantics by inserting the module into `sys.modules` before execution, or prefer a normal package import where practical.
- **Verification:** fresh GitHub Actions run required on the updated PR head.

## 2026-08-19 — Rendering benchmark scoring weights were untested per-metric

- **Observed failure risk:** `prototypes/rendering-benchmark/benchmark.py:score_result()` is the formula that produces the weighted score behind the Phase 1 engine recommendation (`decision_packet.py` → `PHASE1_EXIT_GATE.md`). Its `DEFAULT_WEIGHTS` dict deliberately assigns different weights per metric (comment: "Weights intentionally favor the things that are hardest to retrofit later"), but every existing test (`test_benchmark.py`, `test_decision_packet.py`, `test_normalization.py`) passed a metrics vector with the same value repeated across all thirteen `REQUIRED_METRICS` (uniform 8.0, or one outlier metric in `test_differentiators_are_sorted_by_weighted_effect`). A uniform vector makes `score_result` collapse to `value * sum(weights)`, which is identical regardless of which weight is paired with which metric name, so no test could detect two weights being swapped between metrics (e.g. a future rebalancing edit or refactor that iterates `REQUIRED_METRICS`/`DEFAULT_WEIGHTS` out of step).
- **Root cause:** all prior scoring tests used degenerate (uniform, or single-outlier) input data that happened to make the per-metric weighting mechanism unobservable, so passing tests gave no real assurance the weight-to-metric wiring was correct.
- **Fix:** added `test_score_applies_each_metrics_own_declared_weight` to `prototypes/rendering-benchmark/test_benchmark.py`, using thirteen distinct per-metric values and asserting `score_result()` against a literal expected weighted sum computed independently of `benchmark.py`'s own iteration.
- **Scope:** test coverage only; `benchmark.py`, `decision_packet.py`, and `normalization.py` behavior unchanged.
- **Prevention:** when a weighted/keyed formula is safety- or decision-relevant, cover it with at least one test whose input values are all distinct so the mapping between keys and their weights/coefficients is actually exercised, not just their sum or count.
- **Verification:** confirmed the new test fails (`4.605 != 5.325`) when `DEFAULT_WEIGHTS["visual_fidelity"]` and `DEFAULT_WEIGHTS["memory_use"]` are deliberately swapped, and that every other test in `test_benchmark.py`, `test_decision_packet.py`, and `test_normalization.py` still passes under that same mutation (proving the pre-existing suite could not have caught it). Reverted the mutation; full `prototypes/rendering-benchmark` suite (113 tests) and the complete Foundation checks command sequence pass clean.

## 2026-08-22 — EnergyConsumption boundary test's exact-depletion tick count truncated instead of rounding up

- **Observed failure:** `src/simulation/tests/simulation_core_tests.cpp`'s `EnergyConsumption: boundary case` test (added by PR #74) failed deterministically on a clean build of `main` (commit `f8c1633`, before any change in this slice): `Assertion 'depletion_events.size() == 2' failed`, discovered incidentally while adding a new passive-cooling thermal test to the same file and running the full CTest suite as a green baseline.
- **Root cause:** the test computes `exact_depletion_seconds = initial_energy / capacity_w` (`5.0e8 / 750.0 = 666666.6666...`), then converts that to a whole tick count via `static_cast<std::int64_t>(exact_depletion_seconds * TicksPerSecond)`, which truncates toward zero. Truncation drops a fractional tick, so converting the resulting tick count back to seconds (`ticks / TicksPerSecond`) yields a value fractionally *less* than `exact_depletion_seconds`. `SimulationCore::integrate_power_consumption` then computes `remaining_energy_j = initial_energy - capacity_w * seconds`, which lands at `+0.0004999...` J — positive, not `<= 0.0` — so the `previous_energy_j > 0.0 && remaining_energy_j <= 0.0` transition guard never fires and `EnergyDepleted` is never emitted, even though the test's own tolerant `nearly_equal(..., 0.0, 1e-3)` assertion on `stored_energy_j` still passed (0.0005 is well within a 1e-3 tolerance), masking the event-count failure as the only visible symptom. Confirmed numerically in isolation (Python): `int(666666.6666666666 * 1_000_000) = 666666666666` ticks, converting back gives `stored_energy_j = 0.0004999637603759766`, strictly positive.
- **Fix:** changed the tick-count conversion from `static_cast<std::int64_t>(exact_depletion_seconds * TicksPerSecond)` to `static_cast<std::int64_t>(std::ceil(exact_depletion_seconds * TicksPerSecond))` in that one test, guaranteeing the whole-tick elapsed time reaches or exceeds `exact_depletion_seconds` so `remaining_energy_j` lands at or below zero and the clamp-to-zero/`EnergyDepleted` path is actually exercised. No `SimulationCore` production code changed — the depletion-clamp and event-transition logic in `core.hpp` was already correct; only the test's own tick rounding was wrong.
- **Scope:** test correction only, isolated to this one boundary-case test in `simulation_core_tests.cpp`. `SimulationCore::integrate_power_consumption`, `allocate_power`, movement, scan, and thermal-load/passive-cooling behavior are unchanged.
- **Prevention:** when a test derives a whole-tick (or otherwise discretized) duration from a `seconds = joules / watts`-style non-terminating division and then asserts a boundary *event* (not just a tolerant value comparison) that depends on which side of that boundary the discretized duration lands, round in the direction that guarantees crossing the boundary (`ceil` for "at least this much time must have elapsed") rather than truncating, and do not rely on a tolerant value assertion elsewhere in the same test to mask a wrong-side rounding error.
- **Verification:** confirmed the failure reproduces identically on a clean checkout of `main` (commit `f8c1633`, before this slice's changes) via `cmake -S src/simulation -B build_orig && cmake --build build_orig && ctest --test-dir build_orig --output-on-failure`, isolating it from the new passive-cooling changes landing alongside this fix. ## 2026-08-22 — Every simulation-core CTest assertion was silently disabled by CI's own Release build type

- **Observed failure risk:** `.github/workflows/foundation.yml`'s `repository-constitution` job configures, builds, and runs the production simulation core with `cmake -S src/simulation -B build/simulation -DCMAKE_BUILD_TYPE=Release` followed by `ctest --test-dir build/simulation --output-on-failure`. `src/simulation/tests/simulation_core_tests.cpp` (the only test target this CMake project builds) validates every one of its cases exclusively through `assert()` from `<cassert>`. CMake's `Release` build type passes `-DNDEBUG` (confirmed directly: `grep NDEBUG build/simulation/CMakeFiles/everward_simulation_tests.dir/flags.make` → `CXX_FLAGS = -O3 -DNDEBUG -std=gnu++20`), and the C/C++ standard defines `assert()` as a no-op whenever `NDEBUG` is defined at the point `<cassert>`/`<assert.h>` is processed. That means every `assert()` in the file — all of them, across every slice from `ScanCommand` (PR #72) through `EnergyDepletionResponse` (this slice) — compiled to nothing under the exact command CI runs. The test binary still executes every code path (so a crash, thrown exception, or infinite loop would still be caught), but no logical assertion inside it can ever fail: `ctest` reports "Passed" unconditionally regardless of whether the values, event sequences, or capability flags being checked were actually correct. Confirmed directly: reverting `assert(depletion_core.snapshot().is_energy_depleted)` to its logical opposite, `assert(!depletion_core.snapshot().is_energy_depleted)` — a definitely-false, test-breaking mutation — still produced `ctest --test-dir build/simulation --output-on-failure` (Release) reporting `100% tests passed, 0 tests failed out of 1` until the NDEBUG fix below was applied; after the fix, the identical mutation correctly produced `Subprocess aborted` / `0% tests passed` with the exact failing assertion's file/line in the output, and reverting the mutation returned to a genuine pass.
- **Root cause:** the CI workflow's `-DCMAKE_BUILD_TYPE=Release` configure step (present since PR #68's `6e75c3f`, i.e. since the C++ simulation core and its CTest coverage were first introduced, and unchanged through every subsequent simulation-core PR) and the test file's exclusive reliance on bare `assert()` were each individually reasonable choices (Release matches production compile settings; `assert()` matches this file's own established convention) but were never checked together against the standard library's NDEBUG contract. This is the same class of gap as every other entry in this ledger — a validation mechanism that looked like it was checking something but silently was not — except here it affected the validation mechanism itself (CTest) rather than one of the things CTest validates, and at 100% breadth (every assertion in the only C++ test target) rather than a partial per-key/per-branch gap.
- **Fix:** added `#undef NDEBUG` immediately before `#include <cassert>` at the top of `simulation_core_tests.cpp`, with a comment explaining why. `<cassert>`/`assert.h` is deliberately not include-guarded by the standard specifically so it can be re-included after `#undef NDEBUG` to force active assertions in one translation unit regardless of the build type or any earlier `-DNDEBUG` command-line define; this is the smallest, most portable fix available. No `CMakeLists.txt` change was made (no need to touch the Release optimization flags themselves) and no other file in the repository was affected — this file is the only exclusively-`assert()`-based test target in the CTest suite (the Python prototype/tool suites all use `unittest`'s `assertX` methods, which are unaffected by `NDEBUG` and were not implicated).
- **Scope:** one file, `src/simulation/tests/simulation_core_tests.cpp` — a five-line addition (comment plus `#undef NDEBUG`) before its existing `#include <cassert>`. No `SimulationCore` production code changed as part of this fix itself (the energy-depletion production behavior added in the same commit is a separate, intentional change; see the `PROJECT_STATUS.md` entry for this slice).
- **Prevention:** any C++ test target that uses bare `assert()` (rather than a dedicated test-framework macro that fails independently of `NDEBUG`, e.g. GoogleTest's `EXPECT_*`/`ASSERT_*`) must neutralize `NDEBUG` itself rather than relying on the surrounding build never defining it — a build-type change made for an unrelated reason (matching production optimization settings, as `-DCMAKE_BUILD_TYPE=Release` reasonably does here) can silently disable every assertion in such a file with no compiler warning and no test-runner-visible signal, since the binary still runs and exits zero. When introducing a new C++ CTest target in this repository, prefer either this `#undef NDEBUG` guard or a framework whose failure macros are not conditional on `NDEBUG`, and verify the choice the same way this entry did: deliberately break one assertion and confirm the exact CI-configured build/test command actually reports the failure, not just a local debug-mode compile.
- **Verification:** reproduced the masking directly against the exact CI command sequence (`cmake -S src/simulation -B build/simulation -DCMAKE_BUILD_TYPE=Release && cmake --build build/simulation --parallel 2 && ctest --test-dir build/simulation --output-on-failure`) both before and after the fix, using the deliberate-mutation method described above (also independently reproduced against a fresh clone of `main` at commit `b7f4d6c`, confirming the masking predates this slice entirely). After the fix: the same Release `ctest` command now correctly fails on a broken assertion (with file/line in the output) and correctly passes once reverted; a separate strict `g++ -std=c++20 -Wall -Wextra -Wpedantic` compile with assertions active produces no warnings and passes. Making assertions genuinely active also surfaced one previously-masked, unrelated stale-assumption defect in the pre-existing `EnergyConsumption: boundary case` test, fixed in the same commit — see that test's updated in-file comment for its own root cause and fix, which is specific to that one test's chosen wattage rather than this NDEBUG issue. No other assertion in the file was found to fail once made real, but that was confirmed only as an incidental side effect of this slice's own full-suite run, not a systematic per-assertion audit of every earlier slice; `PROJECT_STATUS.md` names a dedicated follow-up to perform that audit deliberately.
