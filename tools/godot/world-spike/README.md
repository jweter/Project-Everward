# Everward Godot world spike (feasibility test, not game code)

Owner question (2026-11-27): can Godot deliver the Everward world feel if Unreal is unusable on the dev laptop? This is a working test of four things, built so it can be re-run and judged:

1. **Clouds that part around the ship.** A raymarched volumetric cloud layer (`cloud.gdshader`, drawn as a full-screen quad, depth-aware so mountains occlude it). The ship's recent positions are passed in as a trail; each point opens a cavity and pushes the noise pattern outward, and the radius shrinks as the point ages so the cloud recovers.
2. **Trees that shake when the ship flies near.** `tree.gdshader` adds ambient wind sway plus a proximity shake and lean-away, scaled by height so roots stay planted. Trees are a `MultiMesh` placed by raycasting the terrain.
3. **A mountain you can drill, hollow out and watch crumble.** Smooth voxel terrain from the Voxel Tools module (`VoxelTerrain` + `VoxelGeneratorNoise2D` + Transvoxel mesher). Drilling and hollowing are real `VoxelTool.do_sphere` removals with live remeshing and collision. "Crumble" is progressive: the cavity ceiling lets go in pieces, each a real voxel removal plus Jolt rigid-body rubble and a dust puff.
4. **Frame rate on weak hardware.** Everything runs on the dev laptop's Intel Iris Xe integrated GPU.

## Run it

Needs a Godot 4.7.x **with the Voxel Tools module compiled in**, for example `godot.windows.editor.x86_64.exe` from https://github.com/Zylann/godot_voxel/releases (v1.7 is Godot 4.7.2). Nothing is downloaded or installed by this project.

    # scripted flight: writes screenshots and metrics.txt, then quits (~30 s)
    godot.windows.editor.x86_64.exe --path tools/godot/world-spike --resolution 960x540 -- --autotest --out=D:\some\folder

    # fly it yourself
    godot.windows.editor.x86_64.exe --path tools/godot/world-spike
    #   W/S thrust, mouse look, A/D strafe, Q/E down/up, Shift boost,
    #   left mouse or F drill, H hollow out ahead, F12 screenshot,
    #   Esc releases the mouse (Esc again, or a click in the window, recaptures it)

Looks: add `--look=ember_dusk|moonrise|storm_ridge|autumn_mist` to any run to apply a palette from the owner's references (`looks.gd`; see `docs/LOOK_DEVELOPMENT.md`). `-- --lookshots --look=NAME --out=FOLDER` renders the same three framings for comparison and exits 0.

Simulation-driven flight (Godot path G2): `-- --simflight` makes the Everward simulation move the ship through the `EverwardSim` extension from `tools/godot/sim-binding` (build it first; `everward_sim.gdextension` here points at its DLL, and a fresh checkout needs one `--headless --import` to register it, which hits the known first-import crash after finishing). Rocks are registered in both Godot and the simulation; contact comes only from the simulation. The run passes (exit 0) only if exactly one contact is reported on the boulder flown into, the ship's Godot position equals the simulated position (mapped from the simulation's x-forward, y-right, z-up frame), and after a 90-degree turn the ship moves where its nose points, and after a +90-degree roll, thrust toward the probe's right moves the ship along its displayed right; otherwise it exits 6 (5 if the extension did not load). Measured headless on the dev laptop: 1 contact at 14 m/s, 0.000000 m position error, heading match 1.0000; with the yaw sign deliberately flipped the run fails (heading -1.0000, exit 6). **Terrain contact.** The simulation only knows spheres, so three large proxy spheres follow the voxel ground around the ship: straight down, along the flight direction and along the nose. Each is placed so its surface touches the ground where that ray hits it, and the simulation decides terrain contact like any other. The sim-flight run adds a nose-down dive that must produce a terrain contact and leave the ship above the ground. Measured: contact after 8.75 s, 3.26 m clearance. With the proxies disabled as a negative control, the ship ended 98.79 m inside the mountain and the run failed. This is an approximation (three spheres of 40 m radius, refreshed every frame), not true terrain collision.

**Fly it yourself on the simulation:** `-- --sim` (needs the extension). W/S/A/D/Q/E become probe-frame thrust, the mouse turns the probe through the simulation, Space stops, Shift boosts. Two rocks are placed ahead of the start. `-- --selftest-sim` drives the real controls with synthetic input, headless: holding W for 1 s gave 18.04 m/s straight along the nose, and a 100 px mouse move turned the probe exactly 12 degrees. `-- --selftest-input` (mouse capture) needs a window and reports SKIP when headless.

**Seeded exploratory first-loop testing:** `-- --exploretest --seed=23 --steps=12 --out=FOLDER` runs a bounded, repeatable sequence of real gameplay inputs through `first_loop.gd`, capturing each key/step/tick in `report.json`. It checks per-step material conservation, storage limits, system integrity and monotonic time, then attempts recovery through the normal scan, arm, auto-approach, mine and resource-funded Fix_It controls, including a mid-session save/load. A failed seed is an actionable replay command, not a claim that every random game state is tested. `--selftest-fail=explore-invariant` is an explicit negative control and must fail (no simulation data is altered). The one-command developer runner includes this mode by default; see `tools/godot/playtest/README.md`. Runs are headless unless specifically authorized otherwise.

**First gameplay loop (Godot path G3):** with `-- --sim` a mineable deposit sits on the ground ahead. R scans it (R again cancels), 1/2 select the port/starboard arm, T deploys or stows it, Y attaches or detaches its tool, P flies to the mining pose the simulation solves for that arm and then moves the arm along a planned collision-free path (P or Space cancels), G mines. The HUD shows the target, scan progress or SURVEYED, the arm, cargo and storage, the simulation's message for every refusal, and a Fix_It line in the Unreal format with all four subsystem integrities. The probe wakes damaged (computation 18%, thermal 22%, sensors 35%, propulsion 40%), so thrust and turning are weaker and scans take longer until Fix_It, which repairs on its own with mined material and stored energy, restores them; `--no-awakening` starts undamaged. Power (#378 G09): K installs the GEN1 BASIC SURVIVAL policy, L clears it, O sets Sensors to the 50 W scan minimum; the HUD's POWER line shows every allocation, the policy and, while scanning is blocked, the simulation's recovery hint, and a refused scan shows its full explanation. `-- --powertest` is the headless run of the G09 drop and recovery through those keys (exit 0 on `POWERTEST PASS`, 9 on a failed check; `--selftest-fail=noclear` skips the clear and must exit 9). Systems panel (#378 G11): Tab shows the four power subsystems and both arms with their live state; [ and ] move the selection with the simulation's `bounded_selection` rule whether or not the panel is open; selecting an arm makes it the arm T/Y/P act on (and 1/2 move the panel selection to match); Enter toggles a power subsystem between 0 W and its operating minimum (sensors 50 W, computation 25 W; propulsion and thermal have none and say so). `-- --hudtest` checks it through the keys (exit 0 on `HUDTEST PASS`, 10 on a failed check; `--selftest-fail=unbounded` swaps in the old unclamped rule and must exit 10). `-- --firstloop` is the headless acceptance run: unsurveyed mining refused, scan and survey, a cancelled rescan keeps the survey (#378 G05), the arm toggle reverses both ways (G06), out-of-reach mining refused, then approach, align and mine with the port arm, the starboard arm, and the starboard arm with the probe yawed 35 degrees (the other arm stowed each time, because `MiningSystem` credits the closest ready arm), Fix_It waiting while nothing is stored and then repairing computation from 18% to 25% with the mined material (#378 G02), and every kilogram accounted for (deposit loss = inventory gain + what Fix_It consumed). It exits 0 on `FIRSTLOOP PASS`, 8 on any failed check; `--selftest-fail=noscan` skips the scan and must exit 8.

**Contact geometry (#378 G07):** `-- --contacttest` checks contact against the simulation's own compound hull (nose 0, centre 1, tail 2, port wing 3, starboard wing 4; `get_hull_samples()`): a body inside an 8 m sphere but outside the hull is not touched, a wing alone touches, the hull turns with the probe, a 12 m/s impact is reported at 12 m/s with damage, and bodies moving on their own (`set_sphere_body_velocity`) hit a stationary probe once and then carry it, with the hull at most one 60 Hz step of the body's travel inside it. It exits 0 on `CONTACTTEST PASS`, 13 on a failed check. This found a core defect, fixed in `software_policy.hpp`: contact was resolved with the probe's absolute velocity, so a moving body hit a stationary probe on every tick (144 contacts at 3 m/s; one 12 m/s hit took computation to 14%). `move_sphere_body` still teleports a body between steps and is not swept; moving bodies should use a velocity.

**Auto-approach safety (#378 G10):** P refuses when the probe's five-sphere hull would hit a body flying straight to the mining pose (the simulation's own contact sweep, `get_approach_blocker`); while flying, the pose is re-solved if the probe turns more than 0.5 degrees or the target moves more than 5 cm, and the approach stops with the reason if the line becomes blocked or the hull touches anything; a turn or target move after alignment withdraws "aligned". `-- --approachtest` runs seven cases through the keys (port arm; starboard arm with the probe yawed 35 degrees; a boulder on the path; a 40 degree turn and a 6 m target move during the approach; a boulder appearing mid-approach; a turn after alignment) and exits 0 on `APPROACHTEST PASS`, 12 on a failed check; `--selftest-fail=staleapproach` restores the pre-G10 approach (solved once, straight line) and must exit 12. The Unreal controller (`EverwardPlayerControllerMiningControls.cpp`) has the same solve-once straight-line approach and is not changed here.

**Evidence report (#378 G04, G12, G13):** `--firstloop`, `--powertest` and `--hudtest` also write `report.json` next to `metrics.txt` (schema `everward.godot.evidence/1`, written by `evidence.gd`): the git commit, branch, dirty state and dirty files of the checkout, the MD5 and size of the EverwardSim library the engine loaded, the engine version and hash, renderer, display, command line, host and process memory, start and end times (UTC), every pressed key, first-loop message and simulation contact with wall milliseconds and simulation seconds, the preconditions and checks with their details, and a verdict. **INCONCLUSIVE** (exit 11) means the run could not establish its own situation and claims nothing about the game: the build identity is unknown (no git, or `--selftest-fail=noidentity`), or the simulation extension did not load (these modes then exit 11, not 5), or `report.json` itself could not be written (a stale read-only report is never taken as this run's result), or a precondition the harness sets up failed (the terrain did not stream, the deposit could not be registered, the starting power state is not canonical; `-- --powertest --selftest-fail=lowstart` starts with sensors unpowered and must exit 11). A failed check after all preconditions hold is a FAIL with the mode's exit code, a finding about the game. A `GODOT_VERIFIED` claim cites a PASS report with `build.known` true and `build.dirty` false. All waits are bounded by timeouts. `--firstloop` now records 2 preconditions and 16 checks (the deposit registration moved from a check to a precondition; the HUD check that names the aligned arm was added).

Every mode also runs `--headless` (no window): screenshots and the image-based tree-shake check are then skipped and say so in `metrics.txt`.

Exit codes for `--autotest`: 0 route completed; 2 terrain did not stream in time; 3 no mountain face found (drilling, hollowing and crumbling skipped); 4 no trees could be placed. `metrics.txt` records the reason. Two self-tests exist for the checks that cannot be seen in screenshots: `-- --selftest-input` drives the real input handler with synthetic Escape and click events and exits 0 on PASS; `-- --autotest --selftest-fail=face` forces the missing-face failure and must exit 3; `-- --simflight --selftest-fail=clearance` makes the final ground-clearance ray miss and must exit 6 (a missing clearance measurement is a failure, never a pass).

Keep the output folder outside the repository; the first launch also writes a `.godot/` import cache that is git-ignored.

## Measured on the dev laptop (Intel Iris Xe, 960x540, Vulkan Forward+, Godot 4.7.2)

| Item | Result |
|---|---|
| Scripted route | 13 screenshots, 0 script errors, about 30 s |
| Frame rate | 44-60 FPS for the whole route; **dips to about 13 FPS for a moment when drilling starts** (remeshing plus a burst of rubble) |

| Terrain | 289/289 sampled columns streamed; peak 204 m, cloud layer 110-240 m so the peak breaks through |
| Voxel edit call | 47 edits, 0.05 ms average (the edit only; meshing happens asynchronously) |
| Tree shake | The vertex displacement runs: at 25x strength a window around the tree changed in 542 of 8100 sampled pixels against 0 in a control window, and the side-by-side off/on frame (`05_compare_off_left_on_right.png`) shows the tree bent differently. **The pixel count is noisy at the default strength**: across runs the tree window changed 208, 844 and 58 pixels while the control window (which also sees cloud and terrain changes) changed 0, 0 and 878. Treat the shake as visually confirmed, not statistically measured. |
| Interactive mode | 900 frames with no input ran with no errors |

## Not verified / known limits

- **How it looks on a real GPU.** Only the integrated GPU was available. Quality settings (cloud steps, shadows, resolution) are untuned for a desktop.
- **Manual controls.** Keyboard and mouse flight, left-click drilling and H hollowing were not exercised by a person; only the scripted path, a no-input smoke run and the Escape/click mouse-capture self-test were.
- **Crumble is scripted, not structural.** Pieces of ceiling are removed in sequence; disconnected rock does not detect itself and fall. True structural collapse needs a connectivity pass (flood fill) that is not built.
- **Cloud displacement is a visual trick** (trail cavity plus noise push), not a fluid simulation.
- **Art is placeholder**: cone trees, a capsule ship, a procedural terrain shader, hazy hollow interiors (fog and sky ambient need tuning), and no sound.
- The Voxel Tools binary is a third-party prebuilt Godot build; its SHA-256 was recorded at download (`e2292adb0b671508ab220fce5bcd052b1c20674a3385d89c6b38601e6e1f956b`) but the upstream project publishes no checksum to compare against.
- No connection to `src/simulation`. This project does not read or change the game's rules; an engine move would bind them via GDExtension.
